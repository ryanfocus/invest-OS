# 進場改成開盤前起跑、開盤價一到就下單

2026-11-23 定案。取代原本「08:50 叫醒、取開盤價、下單」的時間表。

| 時刻 | 做什麼 |
|------|--------|
| 08:44 | 排程叫醒 → 登入、查商品清單、訂閱三個商品的報價、準備下單（實測約 9 秒） |
| 08:45:05 | 第一次讀開盤價 → 拿齊就算訊號、發 Discord、送單 |
| ～08:46 | 沒拿齊就每 1 秒重讀 |
| 08:46 | 還沒拿齊 → 重新連報價主機一次，之後每 10 秒重讀 |
| `entry_cutoff`（08:50） | 放棄，發「今日無訊號」；過了它也不下單 |

## 為什麼

**回測**（大台日盤逐筆資料 2020/2–2026/11，三商品版 2024/7 起）：08:46 進場每筆 +55.8 點，
08:50 進場 +52.9 點。報酬集中在 09:00–10:00，越早進場越好；08:45–08:46 這一分鐘平均接近 0，
所以開盤後幾秒內進場等同 08:46。

**實測**（2026-11-23，`claude/os-open-price-probe` 分支的探測程式）：

- 三個商品的第一筆真實成交 **08:45:00.28** 就到本機，`nOpen` 欄位同時有值，之後不再變。
  每一秒的成交在那一秒結束後 0.15～0.33 秒內送達。
- 開盤前 `nOpen` 一直是 0、試撮旗標為 1——**但交易日欄位已經是當天**。
  所以「交易日＝今天」不能拿來判斷開盤價好了沒，要看開盤價非 0（`build_open_prices` 本來就這樣檢查）。
- 每 0.2 秒讀一次、連讀 6 分鐘，沒有任何一次失敗；08:45:05 連讀三個商品總共 1 毫秒。
  讀的是訂閱後推進本機元件的資料，**不會打到群益的伺服器**，所以每秒重讀沒有被擋的問題。
- 原本 08:50 第一次讀常常拿到 0，是因為訂閱後只等「任一個商品」的報價就讀三個——
  另外兩個還在路上。同一天探測程式 08:45:00 就讀得到。現在訂閱後等三個都到齊。

**時刻是使用者決定的**：08:45:05 第一次讀、試到 08:50。其餘節奏（每秒、08:46 重連一次、每 10 秒）
是工程選擇，常數在 `main.py` 開頭。

## 放棄時刻與進場界線合併成 `entry_cutoff`

原本有兩個時間：程式裡寫死的「試到 08:50 放棄」，與設定檔的 `entry_cutoff: "09:00"`（過了不下單）。
它們管的事不同——前者是**等報價等多久**，後者是**太晚才跑的那一班准不准送單**（排程補跑時
開盤價一讀就到，放棄時刻根本用不上；沒有界線的話，13:40 之後補跑開的部位會直接過夜）。

但改成開盤前起跑之後，兩者只在「補跑剛好落在 08:50～09:00」時才有差別，分成兩個只會讓人困惑。
使用者 2026-11-23 決定合併：**`entry_cutoff` 一個時間管兩件事，設成 08:50。**

- 拿不到開盤價就試到 `entry_cutoff`；過了它不下單（訊號與觀測記錄照常）。
- 補跑時已過界線：照樣讀價（最少試一分鐘）、發訊號、留觀測記錄，但不下單。
- `entry_cutoff: none`：不限下單時間，開盤價最多只試一分鐘。
- 「這班太晚了」的訊息時刻改寫到秒，原因也多講一種（開盤價拖到界線才拿到）。

## 開盤 5 秒後的價格不能當訊號

使用者也問過「開盤 5 秒後取當下的價格」。實測兩天（11/20 回補資料、11/23 即時）都是：
開盤價算出做多，08:45:05 的價格算出不動作。回測報告 10.5 節的大樣本結論相同——訊號只存在
開盤第一筆。**訊號照舊用開盤價，提早的只是下單。**

## 沒有改的

- **登入失敗不重試**：密碼或憑證有問題時重試沒用，券商通常會在密碼連錯幾次後鎖帳號。
  起跑提早的好處是這則告警在開盤前就到。
- **送單不自動重送**：被拒多半是固定原因（例如 980 倉別），重送一樣被拒；開盤第一秒微台就有
  四百多筆成交，IOC 0 口的機會很低。在動到錢的那一步加邏輯，風險比好處大。
- **不加備援觸發**：「程式安靜地當掉」至今沒發生過，而讓重跑變安全要在下單路徑上加邏輯。
  每天那則訊號本身就是心跳。
- **進場界線保留**（併入 `entry_cutoff`，見上），但改成比「要下單的那一刻」，不是起跑時間——
  重試可能拖幾分鐘，補跑的那一班更可能在途中跨過界線。

## 順便修的

- **0 口成交現在會通知**（⚠️ 委託沒有成交）。原本只記 log、以 0 結束，使用者手上只有那則訊號，
  會以為已經進場。
- **取商品清單時連不上報價主機**，原本落到「非預期錯誤」整天以致命錯誤結束；現在跟開盤價
  一樣重試到 `entry_cutoff`。
- **下單準備做到一半失敗、再做一次時，只從失敗的那一步接著做**。重頭做的話，第二次讀憑證
  群益回 2005「驗章已過」，會被當成失敗。

## Code review 之後（2026-11-23）

規範、規格兩軸審查後，使用者授權由開發端判斷要修哪些。已修：

- **補測試**：訂閱後等三個商品到齊、重連會清掉舊狀態、重連失敗不假裝已訂閱、
  `SystemClock` 睡覺時有跑訊息幫浦（`tests/test_quote_subscription.py`）；
  開盤前訂閱失敗照常繼續、非預期錯誤當致命、重連失敗照樣試到界線（假 broker 現在能注入這些失敗）。
- **排程與時間表的漂移測試**（`tests/test_schedule_matches_timetable.py`）：`setup_schedule.ps1` 的
  進場時間必須比 08:45:05 早 1～10 分鐘；出貨的 `entry_cutoff` 必須晚於第一次讀價。
- **`SystemClock` 搬進 `broker.capital`**：睡覺時跑 COM 訊息幫浦是群益元件的事，broker 是唯一出入口。
- **舊設定檔留著 `quote.retry_*` 時在 log 提醒可以刪**（`settings.obsolete_keys`），載入照常。
- **SPEC 依新策略改寫**（使用者：「應該要以新策略為主」），全 repo 指「08:50 進場」的舊說法一併更新。

確認過、**不改行為，只寫明**的時間表細節：

- 每秒重讀的 55 秒與「最少試一分鐘」都從**第一次讀**起算，不是牆上時鐘。正常日子第一次讀就在
  08:45:05，兩者一樣；起跑或查商品清單拖慢時，這樣才不會一開始讀就只剩一次機會。
  代價是讀價最晚可能超過界線一點點——過了界線不下單，沒有資金風險。
- **重連只由流程主動做一次**；重連失敗時，之後每一次讀價 broker 都會再試著連（每次最多卡住約 45 秒）。
  連線真的斷了，繼續試是對的；最後一次可能超過界線幾十秒才放棄。
- 界線比的是「決定要下單的那一刻」。開盤前的下單準備若失敗，送單時要補做約 3 秒，實際送出可能
  比界線晚幾秒——可接受。
- 0 口成交以非零碼結束：與「下單失敗」一致，都是「不是預期內的一天」，排程結果欄留下痕跡。

## Consequences

- 流程現在需要時鐘（等到 08:45:05、試到 `entry_cutoff`）。原本的約定是「時間是參數，不是接縫」；
  為了不打破它，`run_entry` 沒拿到時鐘時用 `_SteppedClock`：從 `now` 開始、只有 `sleep`
  會讓時間前進。測試照舊只給 `now` 與一個不做事的 `sleep`；正式環境傳 `SystemClock`，
  它睡覺時會跑 COM 訊息幫浦。
- 設定檔的 `quote.retry_*` 拿掉了。它原本進出場共用，進場改用固定時間表後只剩出場在用，
  所以出場重試改成程式常數 `main.EXIT_RETRY_*`（3 次、間隔 60 秒，即 SPEC 第 25 條）。
  舊設定檔留著那兩個鍵也不會出錯——程式只讀要用的鍵。
- 排程時間由 `tools/setup_schedule.ps1` 建立，改成 08:44。**程式與排程要一起換**：
  舊程式在 08:44 起跑會在開盤前讀到 0，用掉重試；新程式在 08:50 起跑則已到界線，不會下單。
- 設定檔的 `entry_cutoff` 從 `"09:00"` 改成 `"08:50"`。
