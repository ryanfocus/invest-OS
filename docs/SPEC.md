# invest-os — OS 策略開發規格

> 詞彙定義見 [CONTEXT.md](../CONTEXT.md)｜架構決策見 [docs/adr/](adr/)

---

## Problem Statement

使用者手上有一個已回測過的台指期當沖策略（策略作者命名為「OS」），規則很簡單：
每天早上比較大台、小台、微台三者的**開盤價**，決定當天做多、做空或不動作，
08:50 進場、13:40 出場，不留倉過夜。

但要真的執行它，使用者每天必須：在 08:45 開盤後盯著看盤軟體抄下三個開盤價、
心算比大小、在 08:50 之前手動下單、再記得在 13:40 回來平倉。

這件事有三個問題：

1. **時間綁死人**。08:50 和 13:40 都是工作時段，漏掉任一個就是策略失效或部位過夜。
2. **人工比價會錯**。三個數字差距經常只有數十點（實測 138 個交易日，中位極差 0.070%），
   而且有 23.2% 的日子大台夾在中間、應該不動作——這種「看起來很接近但方向未定」的情況最容易誤判。
3. **沒有紀錄**。手動執行不會留下「當天的三個開盤價是多少、為什麼做多」的軌跡，
   事後無法驗證策略是否被正確執行。

## Solution

一個在 Windows 上由工作排程器驅動的自動化程式，每個交易日執行兩次：

- **08:50** — 透過群益 API 取得大台、小台、微台的開盤價，計算訊號方向，
  發報到 Discord，並（在開關開啟時）送出進場委託。
- **13:40** — 讀取當日進場記錄，送出等量反向委託平倉。

使用者只需要設定「下哪一種台指期、幾口」，其餘全自動。Discord 每個交易日都會收到一則
訊息，列出三個開盤價與訊號方向——包含「不動作」的日子，因此**沉默只有一種解釋：今天休市**。

自動下單預設**關閉**。第一階段可只跑訊號，用零金錢風險驗證資料正確性，
確認無誤後再開啟下單。

## User Stories

### 訊號產生

1. 作為策略使用者，我想要程式在每個交易日 08:50 自動取得大台、小台、微台的開盤價，這樣我不必在開盤時盯盤抄價。
2. 作為策略使用者，我想要程式取得的是**當日 AM 盤（日盤）**的開盤價，這樣訊號不會誤用前一日夜盤的價格。
3. 作為策略使用者，我想要當大台開盤價同時大於小台與微台時判定為**做多**，這樣符合策略定義。
4. 作為策略使用者，我想要當大台開盤價同時小於小台與微台時判定為**做空**，這樣符合策略定義。
5. 作為策略使用者，我想要**大台與小台相等**、或**大台與微台相等**時判定為**不動作**，因為那不構成「純大於」或「純小於」。
5a. 作為策略使用者，我想要**小台與微台彼此相等**時規則照常適用（大台高於兩者→做多，低於→做空），因為「相等」只看大台與另兩者的關係。此情況實測佔 **15.9%** 的交易日，不是邊緣案例。
6. 作為策略使用者，我想要三個商品都取**近月合約**的開盤價，這樣比較的基準一致。
7. 作為策略使用者，我想要程式從 API 查詢近月合約月份而非自行推算日期，這樣不會因為假日順延而算錯合約。

### 進場

8. 作為策略使用者，我想要程式在 08:50 依訊號方向送出進場委託，這樣我不必準時守在電腦前。
9. 作為策略使用者，我想要自行設定交易標的是大台、小台還是微台，這樣我可以依資金規模選擇。
10. 作為策略使用者，我想要自行設定每次下幾口，這樣我可以自己控制部位大小與槓桿。
11. 作為策略使用者，我**不**想要程式檢查我的槓桿倍數，這樣我保有完全的口數決定權。
12. 作為策略使用者，我想要進場委託以**市價**送出，這樣確保能成交。
13. 作為策略使用者，我想要委託時效為 **IOC**，這樣不會有掛單殘留在委託簿上造成我不知情的部位。
14. 作為策略使用者，我想要訊號為「不動作」時程式不送出任何委託，這樣不會產生非預期的部位。
15. 作為策略使用者，我想要進場委託**不標記當沖**，這樣萬一出場失敗時保證金是足額的，不會被追繳。
16. 作為策略使用者，我想要程式記錄**實際成交口數**而非委託口數，這樣部分成交時出場數量依然正確。

### 出場

17. 作為策略使用者，我想要程式在 13:40 自動平掉當日部位，這樣我不會忘記而留倉過夜。
18. 作為策略使用者，我想要出場送出的是與進場**等量的反向**委託，這樣只平掉 OS 開的部位。
19. 作為策略使用者，我想要程式**不去動我原本就持有的台指期部位**，這樣 OS 與我自己的操作互不干擾。
20. 作為策略使用者，我想要程式在**結算日**改為 13:30 出場，這樣不會因為合約已停止交易而送不出委託。
21. 作為策略使用者，我想要結算日的出場**不重試**，因為 13:30 後合約已停止交易，重試必然失敗，且未平倉部位會被交易所自動現金結算。
22. 作為策略使用者，我想要程式從 API 取得的「最後交易日」來判定結算日，這樣不會因颱風假順延而判斷錯誤。
23. 作為策略使用者，我想要當日訊號為「不動作」時 13:40 不做任何事，這樣不會憑空開出新部位。

### 失敗處理

24. 作為策略使用者，我想要 08:50 取不到開盤價時每隔 1 分鐘重試、最多 3 次，這樣短暫的資料延遲不會讓我錯過整天。
25. 作為策略使用者，我想要 13:40 出場失敗時每隔 1 分鐘重試、最多 3 次，這樣暫時性的失敗有機會自動復原。
26. 作為策略使用者，我想要出場三次都失敗時收到 **Discord 告警**，這樣我能立刻手動處理，不會在不知情的狀況下讓部位進入夜盤。
27. 作為策略使用者，我想要開盤價為 0 或不在漲跌停範圍內時視為「資料未就緒」而重試，這樣不會拿髒值算訊號。
28. 作為策略使用者，我想要進場三次都失敗時當天放棄並發 Discord 告知，這樣我知道今天沒有部位。
29. 作為策略使用者，我想要任何失敗都留下 log，這樣事後能追查原因。

### 通知

30. 作為策略使用者，我想要每個交易日收到一則 Discord 訊息，列出三個開盤價與訊號方向，這樣我知道程式有跑、也知道今天的判斷依據。
31. 作為策略使用者，我想要「不動作」的日子**也收到訊息**，這樣沉默只代表休市，不會與程式故障混淆。
32. 作為策略使用者，我想要**非交易日完全沒有訊息**，這樣不會被假日的雜訊打擾。
33. 作為策略使用者，我**不**想要每天收到例行的出場通知，這樣訊息量維持在每天一則。
34. 作為策略使用者，我想要訊號發報在下單**之前**完成，這樣即使下單環節出問題，我仍然知道今天該有什麼訊號。

### 開關與設定

35. 作為策略使用者，我想要能單獨開關「自動下單」，這樣我可以先只看訊號、不冒金錢風險。
36. 作為策略使用者，我想要自動下單**預設關閉**，這樣不會因為忘記設定而意外下單。
37. 作為策略使用者，我想要能單獨開關「Discord 通知」，這樣測試期間可以不打擾頻道。
38. 作為策略使用者，我想要在「只發 Discord、不下單」的模式下程式完全不呼叫任何下單 API，這樣關閉是真的關閉。
39. 作為策略使用者，我想要把帳號密碼放在設定檔中，這樣程式能在無人值守下登入。
40. 作為策略使用者，我想要程式自動登入而不需要我輸入驗證碼，這樣我再忙也不影響策略執行。

### 資料正確性

41. 作為策略使用者，我想要程式在隔天早上比對前一日的開盤價與期交所官方資料，這樣能發現「取到錯誤盤別」這類系統性錯誤。
42. 作為策略使用者，我想要對帳在當日所有工作完成**之後**才執行，這樣它絕不會耽誤當天的訊號或下單。
43. 作為策略使用者，我想要對帳失敗時只記 log、不影響策略運作，這樣它是純加分功能。
44. 作為策略使用者，我想要對帳發現不一致時收到 Discord 通知，這樣我能及早停用下單並調查。
45. 作為策略使用者，我想要非交易日不執行任何動作，這樣不會在休市日產生錯誤資料。

### 可靠度

46. 作為策略使用者，我想要程式重複執行時不會重複下單，這樣手動重跑或排程異常不會造成雙倍部位。
47. 作為策略使用者，我想要狀態檔以原子方式寫入，這樣斷電不會產生半個檔案導致隔天無法出場。
48. 作為策略使用者，我想要 08:50 與 13:40 是兩次獨立執行，這樣即使早上的程式異常結束，下午的出場仍會被觸發。

### 開發與維運

49. 作為開發者，我想要能在沒有安裝群益 COM 元件的機器上執行全部測試，這樣開發不被環境阻塞。
50. 作為開發者，我想要 COM 元件在函式內才初始化而非模組載入時，這樣 `import` 不會在無 COM 的機器上失敗。
51. 作為開發者，我想要一套測試能同時對假 broker 與真實 COM 執行，這樣可以在真機驗證同樣的行為。
52. 作為開發者，我想要把「時間」當參數傳入而非讀取系統時鐘，這樣測試結算日與非交易日只需換參數。
53. 作為維運者，我想要一份登入設定的步驟文件，這樣換機器時能重建環境。

## Implementation Decisions

### 模組劃分

大致沿用 invest-hm 的慣例（模組層級函式 + `monkeypatch`），但**`broker` 與通知改用依賴注入**：
`run_entry` / `run_exit` 把 broker 與通知當參數收，而非在函式內建立後由測試 monkeypatch。

> 📌 **2026-08-02 修訂**（原文寫「不引入 class 或正式介面」）。
> 改變理由是本文件自己的另一條要求：「自動下單關閉時，broker 的下單函式**一次都沒被呼叫**」
> 必須由測試證明。要證明「零呼叫」就得能觀察呼叫紀錄，注入一個會記錄的假物件
> 遠比 monkeypatch 全域狀態直接。`market_data` 等純函式邊界仍用 monkeypatch。

| 模組 | 職責 |
|------|------|
| `main` | 兩個進入點：進場流程、出場流程。負責流程編排與重試 |
| `strategy` | **純函式**：輸入三個開盤價，輸出訊號方向。無 I/O、無狀態 |
| `broker` | 群益 API 的唯一出入口：登入、查商品清單、取開盤價、送委託、收成交回報 |
| `position_state` | 狀態檔讀寫，原子寫入 |
| `market_data` | 期交所 OpenAPI，供 L3 對帳使用 |
| `notifiers.discord` | Discord webhook |
| `calendar_tw` | **沿用 invest-hm 既有實作**，判定交易日 |

### 兩個進入點的流程

**進場（08:50）**

1. 判定交易日；非交易日 → 靜默結束
2. 檢查狀態檔是否已有今日記錄 → 有則跳過（重複執行保護）
3. 登入群益 → 查詢近月合約與最後交易日 → 訂閱三商品報價
4. 取三個開盤價，套用就緒與不變量檢查；未通過 → 等 1 分鐘重試，最多 3 次
5. 計算訊號
6. 發 Discord
7. 若自動下單開啟且訊號非「不動作」→ 送出進場委託
8. 收到成交回報後**立即**寫入狀態檔（記錄實際成交口數）
9. — 關鍵路徑結束 —
10. L3 對帳：讀昨日記錄、查期交所 OpenAPI、比對、不符則發 Discord。整段包在例外處理內

**出場（13:40／結算日 13:30）**

1. 判定交易日；非交易日 → 靜默結束
2. 讀狀態檔；無今日記錄或訊號為「不動作」→ 結束
3. 登入群益 → 送出等量反向委託
4. 失敗 → 等 1 分鐘重試，最多 3 次（**結算日不重試**）
5. 全部失敗 → 發 Discord 告警
6. 成功 → 更新狀態檔為已出場

### 開盤價取得

依 [ADR-0002](adr/0002-open-price-from-quote-not-kline.md)：取即時報價物件的開盤價欄位，不使用 K 線。

三層防護：

| 層 | 內容 |
|----|------|
| **L0 新鮮度** | 報價的 `nTradingDay` 必須等於今天 |
| L1 就緒判定 | 等連線就緒事件 + 訂閱成功；開盤價為 0 視為未就緒 → 重試 |
| L2 不變量 | 開盤價須落在跌停價與漲停價之間（同一報價物件即含此二欄位） |
| L3 隔日對帳 | 比對期交所 OpenAPI 的官方開盤價 |

⚠️ **L0 是唯一擋得住「看起來完全正常的錯誤」的一層。**
休市或報價尚未換日時，群益不會回「沒有資料」，而是繼續給**上一個交易日**的價格——
非 0、在漲跌停內、數值合理，L1 與 L2 全部會放行。
2026-08-09（週日）實測：程式取到的是 08-07 的開盤價，並蓋上當天日期發了 Discord。

`nTradingDay` 這個欄位**官方文件完全沒提**，是直接向 COM 型別庫查詢結構欄位才找到的。
它的語意經實測確認：AM 盤代碼回當日（`20260810`），全盤代碼回**次一交易日**
（`20260811`，因為進行中的夜盤屬於明天）。

**L0 同時是臨時休市（颱風假）的主防線。** 颱風假的公告多半在前一晚或當天清晨才出來，
設定檔的 `calendar.extra_closures` 常常來不及更新，所以它是補救而不是防護。
真正擋下來的是：期交所沒開市 → 群益繼續給前一個交易日的報價 → 日期對不上 → 不判斷、不下單。
**這條路徑不需要任何人事先做對什麼事**，這正是它可靠的原因。

⚠️ 假 broker 若只回成品 `OpenPrices`，就證明不了 `run_entry` 真的有把今天的日期傳下去
（2026-08-11 突變測試證實：拿掉那行，全部 107 個測試依然通過）。因此 `FakeBroker` 另有
`quotes=` 用法會走真正的 `build_open_prices`，端到端測試一律用它。

**不做**跨來源即時比對——兩個來源若同時取到夜盤價，比對會通過卻仍然下錯單，
原理上無效；且不同表示法（整數 ×100 vs 已處理小數）容易產生假不一致，反而讓策略白白錯過一天。

價格為整數且已放大 100 倍，需除以 100。

### 委託參數

依 [ADR-0003](adr/0003-market-ioc-orders.md)：

| 參數 | 值 |
|------|---|
| 委託價 | 市價 |
| 時效 | IOC |
| 當沖註記 | 否 |
| 倉別（進場） | 待實機驗證（見下） |

**倉別待驗證**：若使用者原本持有反向部位，進場委託會跨越既有部位。
填「新倉」可能被券商拒單，填「自動」則由系統拆為平倉＋新倉。
兩者經濟結果相同，差別在記帳與保證金認定。**須在測試環境實測後才能定案。**

### 商品代號

報價與下單使用兩套不同代碼：

| 商品 | **報價（近月、日盤）** | 下單後台代碼 |
|------|---------------------|-------------|
| 大台 | **`TX00AM`** | `FITX` |
| 小台 | **`MTX00AM`** | `FIMTX` |
| 微台 | **`TM0000AM`** | `FITMF`（**待實機確認**） |

⚠️ **報價代碼必須帶 `AM` 後綴**（＝日盤）。不帶後綴的 `TX00` / `MTX00` / `TM0000`
是**全盤**，開盤價會是夜盤的開盤價——用錯不會報錯，會讓每天的訊號都失準。
2026-08-07 實測確認，見 [ADR-0005](adr/0005-use-am-session-quote-codes.md)。

⚠️ **漲跌停也隨盤別不同**（實測 AM 盤 48990／40084、全盤 48683／39833）。
L2 不變量檢查必須用同一個代碼自己的漲跌停，不可混用。

下單另需指定契約年月（6 碼）。**必須使用「後台代碼 + 明確年月」的寫法**，
不可使用「商品代號 + 月份兩碼」——後者在月份已過期時會**自動改下隔年合約且不報錯**。

商品清單查詢（`RequestStockList(2)`）同時提供**最後交易日**（實測三者皆 `20260819`），
結算日判定直接採用，不必自行推算。

### 部位隔離

程式一律進出「使用者設定的口數」，不因帳上既有部位調整。
出場送出與進場等量的反向委託，使用者原有部位於算術上自然回復。

策略作者原話：「只出場 OS 策略 user 設定的台指期，**原本就持有的台指期不要動他**」。
他確認過的情境（使用者原有 +1 微台固定持有，OS 設定 3 口，當日做空）：

| 時間 | 動作 | 帳戶淨部位 |
|------|------|-----------|
| 開盤前 | 使用者固定持有 | **+1** |
| 08:50 | OS 賣 3 | +1 − 3 = **−2** |
| 13:40 | OS 買回 3 | −2 + 3 = **+1** ✅ |

**狀態檔是唯一權威**。帳戶查詢無法區分部位歸屬——台灣期貨同商品同月份採淨額計算，
帳上的 −2 可能是「OS 空 2」，也可能是「使用者多 1 + OS 空 3」。

### 狀態檔

- 位置：`state/` 目錄下，比照 invest-hm 的 `state/position.json`
- 內容：日期、訊號方向、交易商品、契約年月、**實際成交口數**、進場價、當前階段（已進場／已出場）
- 寫入：寫暫存檔後 `os.replace()` 原子置換
- 時機：收到成交回報後**下一件事就是寫檔**，中間不插入任何其他工作（不發 Discord、不記 log）

### 設定與機密

- 帳號密碼置於 `.env`（明文），比照 invest-hm
- 交易標的、口數、開關、重試參數置於 `config/settings.yaml`
- **`.gitignore` 必須先於 `.env` 建立**，避免機密進入版控歷史

### 環境限制

群益 API 為 Windows ActiveX COM 元件，**無法在 Linux 執行**，因此本專案不部署於既有的
GCP VM。排程由 Windows 工作排程器驅動，該機器在 08:50 與 13:40 必須處於喚醒狀態。

COM 元件的初始化**必須延遲到函式內**，不可在模組載入時執行，否則未安裝 COM 的機器連
`import` 都會失敗。

## Testing Decisions

### 什麼是好的測試

只測**外部可觀察的行為**，不測實作細節。具體到本專案：

- ✅ 測「給定這三個開盤價，送出了什麼委託」
- ✅ 測「給定這個狀態檔，13:40 平了幾口、什麼方向」
- ✅ 測「自動下單關閉時，broker 的下單函式一次都沒被呼叫」
- ❌ 不測內部 helper 函式的簽章或呼叫次數
      （例外：上一條的「**零**呼叫」是行為斷言，不是實作細節——它證明的是開關真的關了）
- ❌ 不測 log 內容

測試一律從最上層的進場／出場流程打進去，斷言三種外部效果：
**送出的委託**、**產生的 Discord 訊息**、**寫入的狀態檔**。

### 接縫

理想是一個。實際上有一個新接縫、兩個沿用既有慣例的接縫：

| 接縫 | 理由 |
|------|------|
| **`broker`**（新） | 群益 COM 無法在測試環境執行。假實作記錄收到的委託，並回放預設的開盤價與成交回報 |
| `notifiers.discord`（沿用） | 不能真的發訊息。invest-hm 已有此模式 |
| `market_data`（沿用） | 外部 HTTP，比照 invest-hm crawler 的 monkeypatch 手法 |

**時間不做接縫**——`now` 作為參數傳入進場／出場流程。測結算日、非交易日、重試時序
只需更換參數，不需凍結時鐘。此做法與 `calendar_tw` 收日期參數的既有設計一致。

**策略邏輯不需要接縫**——三價比大小為純函式，直接測。

**狀態檔不做接縫**——使用 `tmp_path`，測真實的檔案讀寫（含原子置換行為）。

### 測試範圍

| 模組 | 測什麼 |
|------|--------|
| `strategy` | 三種訊號的完整分支。邊界須涵蓋：大台等於小台、大台等於微台、三者全等（皆為不動作），以及**小台等於微台但大台不同**（仍產生訊號） |
| `main`（進場） | 訊號 → 委託對應、不動作不下單、開關關閉不呼叫下單、重試次數、重複執行保護 |
| `main`（出場） | 等量反向、部分成交後只平實際口數、結算日改 13:30 且不重試、無記錄不動作 |
| `position_state` | 讀寫往返、原子置換、檔案損毀時的行為 |
| `broker`（假實作） | 開盤價的就緒判定與不變量檢查 |
| `market_data` | 對帳比對邏輯、日期不符時靜默跳過、例外不外洩 |
| `notifiers.discord` | 訊息內容含三個開盤價與訊號方向、非交易日不發、出場失敗告警 |
| 設定檔 | `settings.yaml` 的每個 key 都有對應程式讀取，避免設定與程式漂移 |

### 既有前例

invest-hm 的 `tests/` 目錄可直接參照：

- `test_strategy.py`（103 行）— 純函式的分支覆蓋寫法
- `test_position_tracker.py`（50 行）— 狀態計算的純函式測試
- `test_main_integration.py`（92 行）— 從 `main` 打進去的整合測試
- `test_discord.py` / `test_discord_failure.py` — 通知模組與其失敗路徑
- `test_twse.py`（334 行）— monkeypatch 外部依賴、驗證重試次數與參數順序的完整範例
- `test_page_load_timeout.py` — **驗證設定檔與程式常數不漂移**的手法，本專案應比照

### 雙軌執行

同一組測試應能對**假 broker**（快速、每次提交都跑）與**真實 COM**（需帳號與憑證、手動觸發）
各執行一次。真機執行用於確認假實作的行為假設仍然成立。

## Out of Scope

- **停損機制**。策略作者明確決定 08:50 進場後不論漲跌都抱到 13:40，這不是遺漏。
- **槓桿或保證金檢查**。口數由使用者自行計算填入，系統不驗證、不試算、不警告。
- **盤中監控**。策略在開盤時一次定案，盤中不比價、不改單、不看盤。
- **部署至 GCP VM**。群益 API 是 Windows COM，無法在 Linux 執行。
- **回測**。策略已由作者回測完成，本專案只負責執行。
- **多帳戶或多策略並行**。
- **改單與刪單**。IOC 委託不會殘留，不需要刪單功能。
- **與 invest-HW 的整合**。兩者完全獨立，僅共用 `calendar_tw` 的實作慣例。
- **交易績效統計**。Discord 只發報開盤價與訊號方向。

### 使用者原有部位會受到的影響

台灣期貨同帳戶、同商品、同月份採淨額計算，多空無法並存。因此在 OS 做空的日子，
使用者原本持有的多單會在 08:50 被沖銷、13:40 以當時價格重新建立。

口數上完全回復，但**成本基礎會被重設，且多付一趟手續費與期交稅**。
做多日不會發生此情況。若使用者在意長期持有的連續性，唯一的解法是用另一個期貨帳號跑 OS。
此為使用者已知悉並接受的取捨，非技術限制。

### 需求來源與變更紀錄

需求來自與策略作者的對話。以下是**過程中被修正過的決定**，記在這裡是為了避免日後
翻到舊訊息時誤以為規格寫錯：

| 項目 | 最初 | **最終** |
|------|------|---------|
| 出場時間 | 13:30 | **13:40**（結算日仍為 13:30，見上） |
| 進場時間 | （隱含 08:45） | **08:50** |

另有一處澄清值得記下：「大台開盤價同時小於小台與微台」時**不是賣出持股，而是開空單**，
13:40 **買回**平倉。系統因此必須支援雙向部位——這在早期對話中一度被誤解。

「無停損」也是**策略作者明確的決定，不是遺漏**（見 Out of Scope）。

### 結算日的現金結算價（對帳時要記得）

結算日若 13:30 的出場單沒成交，未平倉部位由交易所自動現金結算。成交價是
「當日 13:00–13:30 **加權指數**每筆成交價的簡單算術平均」——那是**現貨指數**，不是期貨價。

該日實際損益因此會與「用期貨價計算的回測」有落差。這不影響策略運作，
但事後比對績效時若發現結算日對不上，原因通常在這裡。

### 訊號分布（實測基準）

以期交所 2026/01–07 共 138 個交易日的官方開盤價回推：

| 訊號 | 天數 | 佔比 |
|------|------|------|
| 做多 | 57 | 41.3% |
| 做空 | 49 | 35.5% |
| 不動作 | 32 | 23.2% |

三商品開盤價極差：中位 0.070%、95th 0.247%、最大 0.374%（約 157 點）；
最小為 0.000%——**三者開在同一價位確實發生過**，「相等 → 不動作」不是假想分支。

此分布可作為上線後的合理性參照：若實際運行的訊號比例與此差距懸殊，應懷疑取值有誤。

### 期交所官方資料來源

`GET https://openapi.taifex.com.tw/v1/DailyMarketReportFut`

免驗證、JSON、實測 0.34 秒，僅回傳最近一個交易日。欄位含 `Date`、`Contract`、
`ContractMonth(Week)`、`Open`、`TradingSession`。以 `TradingSession == "一般"` 過濾日盤。

⚠️ 同網站另有 CSV 端點 `dlFutDataDown`，但查詢範圍超過一個月時會回傳
**HTML 錯誤頁而 HTTP 狀態仍為 200**——典型的靜默失敗。若改用該端點，必須驗證回應內容而非只看狀態碼。
