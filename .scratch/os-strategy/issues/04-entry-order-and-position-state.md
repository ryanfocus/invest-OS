# 04 — 進場下單、狀態檔與開關

**What to build:** 自動下單開關關閉時，程式只發訊號、完全不碰下單 API。
開關開啟時，依訊號方向送出市價 IOC 委託，並在收到成交回報後把**實際成交口數**記進狀態檔——
那份記錄是下午出場時唯一的依據。

**Status:** 程式完成（219 tests passed），但**四項實機驗證未完成，在那之前不可開啟自動下單**

## ⚠️ 更正：群益的「測試環境」不是一般帳戶的模擬環境

開工時我從範例程式的下拉選單（`"正式環境", "正式環境SGX", "測試環境", "測試環境SGX"`）
推論「切到 flag 2 就能安全實打」，並據此加了 `capital.environment` 設定。
**這個推論是錯的。** 官方文件對 `SKCenterLib_SetAuthority` 的原文是：

> 4-1-7 SKCenterLib_SetAuthority
> **(SGX 專線only)** 手動設定特殊功能屬性開啟或關閉。
> 備註：SGX 專線屬性：關閉／開啟：0／1
> Bit 1為環境設定：預設0，代表正式環境
> **一般客戶可忽略此部分**

也就是說那個「測試環境」屬於 **SGX 專線**（新加坡交易所 DMA 專線，
文件另註明「SGX API DMA專線需向營業員申請，方可使用」），不是台指期的模擬盤。
設成 `test` 很可能只是無效——**而「以為切到測試環境所以很安全」比根本不切更危險。**

這個推論還連帶造成一個 regression：原本的實作在登入前**無條件**呼叫
`SetAuthority(0)` 並在非 0 回傳時拋 `LoginFailed`。一般帳戶若回非 0，
整個 08:50 的班就會死在一個它本來根本不需要的呼叫上。
已改成 **`production` 時完全不呼叫**（不呼叫本來就是正式環境），
只有明確要求非正式環境時才呼叫，且失敗時擋下——要了測試沒切成功卻繼續送單，
那些單會進正式環境。

文件裡另有「模擬平台」的痕跡（錯誤碼 2022 `SK_WARNING_MORDER_STOP_SERVICE
停止模擬平台服務通知`、`LeaveMonitor` 提到「不會中斷模擬平台回報連線」），
但**這份文件沒有描述一般客戶如何經由 API 使用它**。要確認只能問營業員。

## 實作備註

**下單代碼與報價代碼是兩回事。** 報價用近月連續代碼 `TX00AM`，下單要指名月份 `TX08`
（官方文件 SendFutureOrderCLR 備註明載）。而且三個商品格式互不相同——
大台 `TX08`、小台 `MTX08`、微台 `TM2608`（多了年份兩碼）——所以是從商品清單**讀出來**的，
不是用規則組字串。找不到對應項就 raise，不退而求其次用連續代碼。

順帶擋掉一個文件明載的地雷：「委託 TX03 如果今年 TX03 已過期，則會自動委託隔年 TX03」。

**市價就是 `bstrPrice = "M"`，而且限 IOC/FOK。** 官方文件的 FUTUREORDER 結構註解寫得很明確，
跟 ADR-0003 選的「市價 IOC」剛好一致——不是巧合，是因為市價本來就只能搭這兩種時效。

**委託參數抽成純函式 `build_future_order_fields`。** 留在 COM 呼叫裡的話，
沒有 Windows 與帳號就一行都驗不到，而這些欄位（當沖、時效、買賣別）寫錯都很貴。
期望值來自 ADR 與官方文件，不是從程式反推。

**回報解析不信任欄位索引。** `OnNewData` 的欄位**位置**是從官方文件的排列推導的，
沒有實機驗證。所以 `parse_reply_row` 驗證形狀（市場別是 TF、Type 是已知代碼、
數量是數字），對不上就回 `None` 讓上層當成「沒收到回報」——
寧可承認不知道，也不要把某個剛好是數字的欄位當成成交口數寫進狀態檔。

**期貨帳號由 `.env` 明確指定**，不從 `OnAccount` 自動挑。有多個帳號時
「自動挑一個」會把單下到使用者沒預期的帳戶上。

**狀態檔讀不懂時拋例外，絕不回 `None`。** 「確實沒有部位」與「檔案壞了」混為一談的話，
出場那一班會以為今天沒進場而什麼都不做，帳上的部位就這樣進夜盤——
這是本系統最貴的失效模式。

## code-review 抓到的東西（2026-08-14）

初版 commit `9d75428` 之後跑了雙軸 review，找到六個真問題，都已修正並突變驗證：

| # | 問題 | 後果 |
|---|------|------|
| 1 | 成交列之後才到的拒絕列會讓整筆判定失敗 | **帳上有部位、程式不知道 → 13:40 不會去平 → 過夜** |
| 2 | 設定檔的 `auto_enabled: "false"`（加引號）是字串，永遠為真 | 使用者以為開關關著，程式照常送真單 |
| 3 | 重複執行保護放在下單那一步，不是 SPEC 的第 2 步 | 重跑會再發一則一模一樣的 Discord |
| 4 | 回報沒依委託序號過濾 | 加總到別人的成交 → 下午平錯口數 |
| 5 | 狀態檔沒存下單代碼 | 出場得重推，結算後會推到次月合約 → 「平倉」變開新倉 |
| 6 | `_order_failed` 把訊號填成 `None`、`notified` 寫死 | 與「無法判斷」撞在一起，對帳分不出發生什麼事 |

第 1 項的規則因此是**不對稱**的：只要有成交就不算失敗（IOC 部分成交後取消剩餘量
是常態），完全沒成交才談失敗。見 `broker/capital.py` 的 `summarize_fills`。

第 5 項還發現一個測試盲點：加了欄位、也測了 `write`/`read` 往返，但**沒有測
`main.py` 真的把值放進去**——突變測試證實把它改成空字串時 183 個測試全綠。
補上端到端斷言與 `PositionRecord.__post_init__` 的驗證後才擋得住。

**明確留給 ticket 05 的**：成交回報逾時目前拋 `OrderFailed`，語意並不精確
（那個例外的意思是「確定沒有部位產生」，但逾時其實是「不知道」）。
正確處理是記為「不確定」並要求人工確認，連同「逾時秒數由設定檔決定」一起屬於 05。
`_await_fill` 的註解標明了這件事。
