## 🐛 2026-08-19 抓到的真實漏洞：序號拿不到時會認領別人的成交

使用者當天換倉（結算日，八月→九月），我趁機開著監聽器抓回報。
那兩列**價差單**的回報意外揭露一個比欄位格式嚴重得多的問題。

**漏洞**：`summarize_fills` 原本寫

```python
if seq and seq not in row:      # ← seq 為空時，整條過濾被跳過
    continue
```

序號拿不到時，視窗內**每一列**期貨回報都被算成自己的成交。

**為什麼這不是理論風險**：回報事件是共用的。使用者手動下的單走同一條線——
當天 11:38 的換倉價差單就出現在 OS 自己的串流上。實測：

```
summarize_fills(換倉的兩列, '')  →  filled_lots=1, matched_rows=2
```

OS 會記下一個**它沒有的部位**，13:40 送出平倉單，而出場倉別是「自動」，
券商不會擋 → **開出反向新倉**。正是整張票開頭警告的那個失效模式。

**而序號來自 `SendFutureOrderCLR` 的回傳訊息，那是整個系統裡唯一
從來沒有真正執行過的 API**——它成功時回不回序號，我們並不知道。

**修法（兩層）**：

- [x] `summarize_fills`：`seq` 為空字串時**一列都不算**
      （空字串是任何字串的子字串，所以拿掉 `seq and` 還不夠，要明確早退）
- [x] `place_order`：序號為空就**立刻** `FillUnknown`，不等 10 秒逾時
      —— 逾時的訊息是「仍未結束」，聽起來像市場沒成交，而真正的問題是認不出來
- [x] ⚠️ `str(None)` 是 `"None"`，一個看起來很正常的非空字串。
      少了 `is None` 判斷，回傳 None 時會拿字面上的 "None" 當序號白等 10 秒。
      **測試差點放過這條**——原本只斷言「有拋 FillUnknown」，
      而它確實有拋，只是**因為別的理由**。加上「沒有進入等待迴圈」才擋住。

結局是 `FillUnknown` 而不是 `OrderFailed`：單確實在市場上了，
說成「確定沒有部位」的話上層不寫狀態檔，13:40 不會去平，部位直接進夜盤。

## ⚠️ 更正：群益的「測試環境」不是一般帳戶的模擬環境

開工時我從範例程式的下拉選單（`"正式環境", "正式環境SGX", "測試環境", "測試環境SGX"`）
推論「切到 flag 2 就能安全實打」，並據此加了 `capital.environment` 設定。
**這個推論是錯的。** 官方文件對 `SKCenterLib_SetAuthority` 的原文是：

> 4-1-7 SKCenterLib_SetAuthority
> **(SGX 專線only)** 手動設定特殊功能屬性開啟或關閉。
> 備註：SGX 專線屬性：關閉／開啟：0／1
> Bit 1為環境設定：預設0，代表正式環境
> **一般客戶可忽略此部分**

也就是說那個「測試環境」屬於 **SGX 專線**（新加坡交易所 DMA 專線，
文件另註明「SGX API DMA專線需向營業員申請，方可使用」），不是台指期的模擬盤。
設成 `test` 很可能只是無效——**而「以為切到測試環境所以很安全」比根本不切更危險。**

這個推論還連帶造成一個 regression：原本的實作在登入前**無條件**呼叫
`SetAuthority(0)` 並在非 0 回傳時拋 `LoginFailed`。一般帳戶若回非 0，
整個 08:50 的班就會死在一個它本來根本不需要的呼叫上。
已改成 **`production` 時完全不呼叫**（不呼叫本來就是正式環境），
只有明確要求非正式環境時才呼叫，且失敗時擋下——要了測試沒切成功卻繼續送單，
那些單會進正式環境。

文件裡另有「模擬平台」的痕跡（錯誤碼 2022 `SK_WARNING_MORDER_STOP_SERVICE
停止模擬平台服務通知`、`LeaveMonitor` 提到「不會中斷模擬平台回報連線」），
但**這份文件沒有描述一般客戶如何經由 API 使用它**。要確認只能問營業員。

## 實作備註

**下單代碼與報價代碼是兩回事。** 報價用近月連續代碼 `TX00AM`，下單要指名月份 `TX08`
（官方文件 SendFutureOrderCLR 備註明載）。而且三個商品格式互不相同——
大台 `TX08`、小台 `MTX08`、微台 `TM2608`（多了年份兩碼）——所以是從商品清單**讀出來**的，
不是用規則組字串。找不到對應項就 raise，不退而求其次用連續代碼。

順帶擋掉一個文件明載的地雷：「委託 TX03 如果今年 TX03 已過期，則會自動委託隔年 TX03」。

**市價就是 `bstrPrice = "M"`，而且限 IOC/FOK。** 官方文件的 FUTUREORDER 結構註解寫得很明確，
跟 ADR-0003 選的「市價 IOC」剛好一致——不是巧合，是因為市價本來就只能搭這兩種時效。

**委託參數抽成純函式 `build_future_order_fields`。** 留在 COM 呼叫裡的話，
沒有 Windows 與帳號就一行都驗不到，而這些欄位（當沖、時效、買賣別）寫錯都很貴。
期望值來自 ADR 與官方文件，不是從程式反推。

**回報解析不信任欄位索引。** `OnNewData` 的欄位**位置**是從官方文件的排列推導的，
沒有實機驗證。所以 `parse_reply_row` 驗證形狀（市場別是 TF、Type 是已知代碼、
數量是數字），對不上就回 `None` 讓上層當成「沒收到回報」——
寧可承認不知道，也不要把某個剛好是數字的欄位當成成交口數寫進狀態檔。

**期貨帳號由 `.env` 明確指定**，不從 `OnAccount` 自動挑。有多個帳號時
「自動挑一個」會把單下到使用者沒預期的帳戶上。

**狀態檔讀不懂時拋例外，絕不回 `None`。** 「確實沒有部位」與「檔案壞了」混為一談的話，
出場那一班會以為今天沒進場而什麼都不做，帳上的部位就這樣進夜盤——
這是本系統最貴的失效模式。

### 這是為了什麼

`sNewClose`（倉別）是 `FUTUREORDER` 裡**唯一一個正確值推不出來、而且填錯不會報錯**
的欄位：

| 值 | 意思 |
|---|------|
| 0 | 新倉 |
| 1 | 平倉 |
| 2 | 自動 |

台指期同帳號同商品同月份採**淨額**計算，而使用者本來就持有微台部位
（見 CONTEXT 的「固定持有部位」）。所以「賣出時填新倉」到底算開空還是減多，
**文件沒說**。填錯的後果不是報錯，是**平倉單被當成新倉、部位不減反增**。

進場與出場是**兩個獨立的未知數**，進場驗過不代表出場的填法就對。

### 執行：**排程負責報時，人負責看著**

⚠️ **不是手動敲指令。** 需要人的是「出事能立刻接管」，不是精準報時——
排程比人準，而使用者平日要上班，抓不到 08:50 那一刻。
（初版寫成「全程手動」，那把兩件事混在一起了。）

| 時間 | 誰 | 動作 |
|------|-----|------|
| 前一晚 | 使用者 | `auto_enabled: true`，**不 commit** |
| 前一晚 | agent | 建立當天的兩個一次性排程（08:50 `entry`、13:40 `exit`）|
| **08:45** | 使用者 | remote 回到對話視窗，叫 agent 開始看 |
| 08:50 | 排程 | `main.py entry` 自動執行 |
| 08:50~ | agent | **即時讀日誌**並回報：三個開盤價、訊號、有沒有送出委託、成交幾口 |
| ↓ | 使用者 | 有狀況 → **在群益 APP 手動接管**（那才是人真正要做的事）|
| **13:35** | 使用者 | remote 回來 |
| 13:40 | 排程 | `main.py exit` 自動執行 |
| 13:40~ | agent | 回報平掉幾口、狀態檔有沒有標 `exited` |
| 收盤後 | agent | 再跑一次 `verify_order_path.py`（**必須當天**，查詢查的是當日紀錄）|
| 收盤後 | 使用者 | `auto_enabled: false`，不可 commit 開啟的狀態 |

**日誌是即時的**（`logging` 走 stderr，Python 3.9 起即使重導到檔案也是行緩衝）——
2026-08-20 實測確認過。所以 agent 可以邊跑邊看，不必等程式結束。

**兩個分支要當場判斷：**

- **訊號「不動作」→ 今天測不成。** 關掉開關，改天再來。不算失敗。
- **委託被拒 → 那就是答案。** 記下錯誤碼，關掉開關，改 `sNewClose` 再測。

**立刻手動接管的條件**：送出委託後 10 秒內沒有成交回報（去 APP 看帳戶，別等程式）、
狀態檔記的口數與 APP 顯示的不符、13:40 出場後帳上仍有殘留。

> 📌 **萬一你臨時走不開，不是災難。** 曝險上限就是 1 口微台，看不看著都一樣；
> Discord 告警照發。「人在旁邊」是為了**學得快、反應快**，不是為了限制損失。
> 所以不必為了守著它而請假。
