# 09 — 成交查詢後備（把「不確定」從常見變罕見）

**What to build:** 等不到推播的成交回報時，**主動查一次**（`GetFulfillReport`），
而不是直接舉手投降。出場那班遇到「不確定」的記錄時也先查一次，查到就自動復原。

**Blocked by:** 05（進場側查詢）、06（出場側復原）

**Status:** ⚠️ **驗收條件要改** —— 2026-08-19 拿到真實回傳，
**本張的核心前提「查一次 `GetFulfillReport` 就好」是錯的**，見下

## 為什麼值得做

目前拿成交結果只有一條路：等群益**推播** `OnNewData`。等不到就記為「不確定」、
發 Discord 叫人去看帳戶、下午拒絕自動平倉——**整天癱瘓，而且要人介入**。

問題是推播這條路很脆弱：它需要 Solace 回報連線正常、事件註冊成功、訊息幫浦持續在跑。
**而且它是一次性的**——訊息送出來的那一瞬間沒接到，就永遠消失了，不會重送。

`GetFulfillReport` 走完全不同的路：

```
4-2 SKOrderLib（下單元件）  → GetFulfillReport   請求／回應，你問它答
4-3 SKReplyLib（回報元件）  → OnNewData          Solace 串流，它主動推
```

不同元件、不同連線、不同通訊方式，而且查詢讀的是**券商主機留存的紀錄**，
什麼時候問都在。失效原因幾乎不重疊：

| 失效原因 | 推播 | 查詢 |
|---|:---:|:---:|
| Solace 回報連線沒建起來／中途斷掉 | ✅ | ❌ |
| 事件沒註冊成功 | ✅ | ❌ |
| 訊息幫浦沒跑到 | ✅ | ❌ |
| 欄位位置推錯認不出那一列 | ✅ | ❌（不同格式，各自出錯） |
| 序號比對失敗 | ✅ | ❌ |
| **成交真的還沒發生** | ✅ | ✅ |
| 群益整個後台掛掉 | ✅ | ✅ |

唯一實質重疊的「成交還沒發生」，對 IOC 而言幾乎不可能——IOC 在交易所端是毫秒級
就有結局的。**等了 10 秒還沒消息，最可能的解釋不是「還在處理」，而是「推播管線壞了」**，
而那正是查詢能救的情況。

## 驗收條件

### 進場側（08:50）

- [ ] ~~推播等不到時，主動查詢**一次**（`GetFulfillReport`）~~
      → **要查兩次，順序不能反**（2026-08-19 實測，見下方「核心前提被推翻」）
- [ ] 推播等不到時，先 `GetOrderReport` 用委託序號找到自己那列、讀出**委託書號**，
      再 `GetFulfillReport` 找委託書號相同的列 → 照常寫入已確認的狀態檔
- [ ] 查詢也查不到 → 才記為「不確定」（維持現有行為）
- [ ] 查詢本身失敗（連線錯誤、格式看不懂）→ 也是記為「不確定」，不可當成「沒成交」
- [ ] 查詢只做一次，不重試——文件限制每次查詢間需間隔五秒，而 08:50 沒有那個時間

### 出場側（13:40）

- [ ] 讀到「不確定」的記錄時，**先查一次**再決定
- [ ] 查到了 → 狀態升級為已確認，**照常自動平倉**（使用者完全不必介入）
- [ ] 仍然查不到 → 才走 ticket 06 的「不自動送單、發 Discord 要人處理」

### 順帶修正一個正式程式的弱點（code-review 2026-08-16）

- [ ] `_ensure_order_ready()` 目前在 `SKReplyLib_ConnectByID` 回傳 0 就認定成功，
      但**那只代表「請求已受理」**——官方文件把 `OnSolaceReplyConnection` /
      `OnComplete` 列為它的通知事件，連線結果是非同步回來的。
      回報連線若靜默失敗，正式程式會照常送單、然後永遠等不到回報
      → 每次都變成「不確定」→ 每天都要人介入。
      改成等連線事件（或至少記錄下來），是本張「讓不確定變罕見」的一部分。

### 通用

- [ ] 查詢回傳的解析**不信任欄位索引**，沿用 `parse_reply_row` 的做法：
      形狀對不上就當成查不到，絕不硬轉成數字
- [ ] 全部行為在假 broker 上可測，不需真實 COM 或帳號

## 🔴 核心前提被推翻（2026-08-19）

使用者結算日換倉，帳上因此有當日成交紀錄，終於拿到兩個查詢的真實回傳
（`tests/fixtures/reports-2026-08-19.txt`）。結果推翻了本張的做法：

**委託序號只存在於其中一種回傳裡。**

| | 委託序號 `2315609394137` |
|---|---|
| `OnNewData` | `[0]` 與 `[47]` ✅ |
| `GetOrderReport` | `[8]` 與 `[9]` ✅ |
| **`GetFulfillReport`** | **完全沒有** ❌ —— `[8]` 是成交編號 `0000006131` |

本張原本寫「推播等不到時，主動查一次（`GetFulfillReport`）」。
**光查那個認不出哪幾列是自己的**——而回報是共用的，使用者的手動交易
就在同一份資料裡（同一天已經證明過一次，見 ticket 04 的序號漏洞）。
認錯的後果是把別人的成交寫進自己的狀態檔，13:40 照那個口數平倉，
多平的部分變成**反向新倉**。

唯一串得起兩份的是 `[7]` 的**委託書號**（本例 `x0582`），三種格式都有。
所以正確做法是**兩段查詢**：

```
1. GetOrderReport   → 用委託序號找到自己那列 → 讀 [7] 委託書號
2. GetFulfillReport → 找 [7] 相同的列 → 加總 [26] 成交口數
```

代價是查兩次。而文件註明「限制每次查詢間需間隔五秒」——
所以這條後備路徑最少要 5 秒以上，設計時要算進去。

### 連帶要處理的三件事

- [ ] **委託書號的唯一性未驗證。** 每筆委託唯一？當日唯一？跨日會重複？
      若跨日重複，隔日殘留的紀錄會被誤認成今天的。
      在驗證之前，比對**必須**同時檢查日期欄（`GetFulfillReport` 的 `[9]`）。
- [ ] **一筆委託可能對到多列成交。** 本例是價差單，一隻腳一列，
      每列 `[26]` 都是 1，整份加總會得到 2 而使用者只換了 1 口。
      OS 自己不下價差單，但**加總前別假設「一列一口」**。
- [ ] **商品代碼有三種寫法**，跨格式比對一定失敗：

      | 用途 | 寫法 |
      |------|------|
      | 報價 | `TM0000AM` |
      | 下單／`OnNewData` | `TM2608`（價差 `TM2608/2609`） |
      | **查詢回傳** | **`TMFH6`**（價差 `TMFH6/I6`） |

      目前沒有跨格式比對的程式碼，但這是很容易長出來的東西。

## 實作備註

**`GetFulfillReport` 的已知限制**（官方文件）：

| 限制 | 影響 |
|---|---|
| 「查詢為阻塞式，請以執行緒方式進行查詢」 | 會卡住程式幾秒。08:50 可以接受，但要設上限 |
| 「限制每次查詢間需間隔五秒」 | 所以只查一次，不做重試迴圈 |
| 回傳以 `,` 分隔、`\r\n` 換行 | 又一組沒實機驗過的欄位位置——同一類風險 |
| `M003: 查無資料` / `M999: 查詢錯誤` | 這兩個要分開處理：查無資料≠查詢失敗 |

**⚠️ 不要用 `GetOpenInterest`（未平倉查詢）代替。** 它回的是**淨額**：
台指期同帳戶同商品同月份採淨額計算，使用者自己的固定持有部位會混在裡面，
分不出哪幾口是 OS 開的（見 CONTEXT 的「固定持有部位」）。
`GetFulfillReport` 查的是我們自己送出的委託，沒有這個問題。

**這張是強化，不是修 bug。** 沒有它系統也是正確的，只是遇到回報延遲時
會要求人工介入。所以優先順序低於 06、07。
