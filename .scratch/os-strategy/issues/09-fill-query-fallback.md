# 09 — 成交查詢後備（把「不確定」從常見變罕見）

**What to build:** 等不到推播的成交回報時，**主動查一次**（`GetFulfillReport`），
而不是直接舉手投降。出場那班遇到「不確定」的記錄時也先查一次，查到就自動復原。

**Blocked by:** 05（進場側查詢）、06（出場側復原）

**Status:** 程式完成（406 tests passed）。
⚠️ **單腳成交列的欄位位置尚未實機驗證**——手上唯一的真實樣本是價差單，
要等里程碑 1 送出第一筆真單才能把期望值釘死

## 為什麼值得做

目前拿成交結果只有一條路：等群益**推播** `OnNewData`。等不到就記為「不確定」、
發 Discord 叫人去看帳戶、下午拒絕自動平倉——**整天癱瘓，而且要人介入**。

問題是推播這條路很脆弱：它需要 Solace 回報連線正常、事件註冊成功、訊息幫浦持續在跑。
**而且它是一次性的**——訊息送出來的那一瞬間沒接到，就永遠消失了，不會重送。

`GetFulfillReport` 走完全不同的路：

```
4-2 SKOrderLib（下單元件）  → GetFulfillReport   請求／回應，你問它答
4-3 SKReplyLib（回報元件）  → OnNewData          Solace 串流，它主動推
```

不同元件、不同連線、不同通訊方式，而且查詢讀的是**券商主機留存的紀錄**，
什麼時候問都在。失效原因幾乎不重疊：

| 失效原因 | 推播 | 查詢 |
|---|:---:|:---:|
| Solace 回報連線沒建起來／中途斷掉 | ✅ | ❌ |
| 事件沒註冊成功 | ✅ | ❌ |
| 訊息幫浦沒跑到 | ✅ | ❌ |
| 欄位位置推錯認不出那一列 | ✅ | ❌（不同格式，各自出錯） |
| 序號比對失敗 | ✅ | ❌ |
| **成交真的還沒發生** | ✅ | ✅ |
| 群益整個後台掛掉 | ✅ | ✅ |

唯一實質重疊的「成交還沒發生」，對 IOC 而言幾乎不可能——IOC 在交易所端是毫秒級
就有結局的。**等了 10 秒還沒消息，最可能的解釋不是「還在處理」，而是「推播管線壞了」**，
而那正是查詢能救的情況。

## 🔴 核心前提被推翻（2026-08-19）

使用者結算日換倉，帳上因此有當日成交紀錄，終於拿到兩個查詢的真實回傳
（`tests/fixtures/reports-2026-08-19.txt`）。結果推翻了本張的做法：

**委託序號只存在於其中一種回傳裡。**

| | 委託序號 `2315609394137` |
|---|---|
| `OnNewData` | `[0]` 與 `[47]` ✅ |
| `GetOrderReport` | `[8]` 與 `[9]` ✅ |
| **`GetFulfillReport`** | **完全沒有** ❌ —— `[8]` 是成交編號 `0000006131` |

本張原本寫「推播等不到時，主動查一次（`GetFulfillReport`）」。
**光查那個認不出哪幾列是自己的**——而回報是共用的，使用者的手動交易
就在同一份資料裡（同一天已經證明過一次，見 ticket 04 的序號漏洞）。
認錯的後果是把別人的成交寫進自己的狀態檔，13:40 照那個口數平倉，
多平的部分變成**反向新倉**。

唯一串得起兩份的是 `[7]` 的**委託書號**（本例 `x0582`），三種格式都有。
所以正確做法是**兩段查詢**：

```
1. GetOrderReport   → 用委託序號找到自己那列 → 讀 [7] 委託書號
2. GetFulfillReport → 找 [7] 相同的列 → 加總 [26] 成交口數
```

代價是查兩次。而文件註明「限制每次查詢間需間隔五秒」——
所以這條後備路徑最少要 5 秒以上，設計時要算進去。

### 連帶要處理的三件事

- [x] **委託書號的唯一性未驗證。** 每筆委託唯一？當日唯一？跨日會重複？
      若跨日重複，隔日殘留的紀錄會被誤認成今天的。
      在驗證之前，比對**必須**同時檢查日期欄（`GetFulfillReport` 的 `[9]`）。
- [x] **一筆委託可能對到多列成交。** 本例是價差單，一隻腳一列，
      每列 `[26]` 都是 1，整份加總會得到 2 而使用者只換了 1 口。
      OS 自己不下價差單，但**加總前別假設「一列一口」**。
- [x] **商品代碼有三種寫法**，跨格式比對一定失敗：

      | 用途 | 寫法 |
      |------|------|
      | 報價 | `TM0000AM` |
      | 下單／`OnNewData` | `TM2608`（價差 `TM2608/2609`） |
      | **查詢回傳** | **`TMFH6`**（價差 `TMFH6/I6`） |

      目前沒有跨格式比對的程式碼，但這是很容易長出來的東西。

## 實作結果（2026-08-19）

```
進場 08:50   place_order 拋 FillUnknown
             → query_filled_lots(序號, 交易日, 委託口數)
               → GetOrderReport   用序號找委託書號
               → sleep 5.5 秒     （文件：查詢間需間隔五秒）
               → GetFulfillReport 用委託書號加總成交口數
             → 查到 N>0  → 寫 CONFIRMED 記錄，當作沒事發生過
             → 查到 0    → 確定沒成交，不寫記錄
             → 查不到    → 維持原本的 UNCERTAIN + Discord 告警

出場 13:40   讀到 UNCERTAIN 記錄
             → 同一套查詢
             → 查到 N>0  → 升級為 CONFIRMED，**照常自動平倉**
             → 查到 0    → 清掉那筆記錄（見下），安靜結束
             → 查不到    → 走 ticket 06 的老路：不送單、發 Discord
```

**三個回答刻意分得很開**：`None`（不知道）、`0`（確定沒有）、`N>0`（確定有）。
把 `None` 當成 `0` 的話，實際成交的部位就沒有人知道、13:40 不會去平，直接進夜盤。

**新增 `state.clear_position()`。** 出場時查到「確定 0 口」要把那筆說「不知道」的
記錄清掉，而不是改寫成 `lots=0`——`PositionRecord` 的不變量刻意規定
`CONFIRMED` 必須有口數 ≥ 1，「確定沒有部位」在這套設計裡就是**沒有記錄**
（進場那條路早就是這樣做的）。留著它等於讓檔案說謊。

### ⚠️ 單腳成交列的欄位位置**尚未實機驗證**

手上唯一的真實成交查詢樣本是**價差單**（使用者換倉）。單腳的列會不會把
第二隻腳那幾欄留白、還是整個往前移，**我們不知道**——這正是當初把微台 CID
推成 `FITMF` 的同一類錯誤。

所以解析除了看欄位，還有四道**與欄位位置無關**的檢查：

| 檢查 | 擋掉什麼 |
|------|---------|
| 日期要對 | 隔日殘留的紀錄（委託書號的唯一性未驗證） |
| **口數不得超過委託量** | 推錯欄位最常見的症狀——抓到一個不相干的數字 |
| 不得是價差列 | 一隻腳一列，加總會得到兩倍 |
| 口數與價格**同時**要說得通 | 欄位整體位移時仍可能剛好撿到一個合法的小數字 |

里程碑 1 送出第一筆真單後，要拿真實的單腳回傳回來把期望值釘死。

### 1. 出場單的不確定被當成進場的不確定 → 重跑會開出反向新倉

```
13:40 送出場單 → FillUnknown → 記錄變成 UNCERTAIN，
                 而 order_seq 被換成**出場單**的序號
重跑         → 拿它去查 → 查到出場單成交的 N 口
             → 程式當成「早上成交 N 口」→ 再送一筆等量反向委託
             → 帳上早就平掉了，第二筆是裸露的反向新倉，沒人管地進夜盤
             → 而狀態檔還說「已了結」
```

本張之前這條路徑是直接拒絕送單並發 Discord，**安全的**。是本張引入的迴歸，
違反 SPEC 使用者故事 46 與 `broker/__init__.py` 的 `FillUnknown` docstring。

**修法**：`PositionRecord` 新增 `uncertain_stage`（`ENTRY` / `EXIT`），
不確定時必填。出場不確定 → **不查詢、不送單、發 Discord 要人確認帳戶**。

為什麼連查都不查：`order_seq` 是出場單的序號，查到的成交是出場單自己的，
看起來卻像「早上成交了 N 口」——查詢在這裡不只沒用，是會誤導。

### 2. 價差守衛對真實資料完全不會觸發

守衛檢查 `[12]` 有沒有斜線，但**真實價差成交列的 `[12]` 放的是單腳代碼**
（`TMFH6` / `TMFI6`），斜線只出現在最後一欄。

而當時的測試之所以綠，是被「超額口數」那道擋下的，不是被這道。
把 `requested_lots` 從 1 改成 2 就破了：

```
parse_filled_lots(真實價差兩列, 'x0582', 20260819, requested_lots=2)  →  2
                                                    ← 別人的成交被算成自己的
```

**修法**：掃整列而不是只看 `[12]`。價格、日期、序號都不含斜線，誤殺機率低；
而誤殺的代價只是回 None → 維持不確定 → 要人看一眼。

### 3. 先查詢後寫檔，打破了「送出後第一件事就是寫檔」

查詢那一步若拋出任何東西，例外會帶著整個函式離開而**什麼都沒寫**——
13:40 會以為今天沒進場，而早上的 Discord 還說「委託沒有送出去」。
**修法**：先寫 UNCERTAIN 記錄，再查詢，查到才升級。

### 4. 開關關著仍然登入並呼叫下單元件的查詢 API

違反 SPEC 使用者故事 38「完全不呼叫任何下單 API，這樣關閉是真的關閉」。
**修法**：開關關著就不查，照舊發「不確定」那則（訊息不需要 broker）。

### 5. 四條測試是空斷言

| 測試 | 為什麼是空的 |
|------|------------|
| 開關順序那條 | `_exit()` 把 `auto_order_enabled=True` 寫死，**根本進不了那個分支**，斷言恆真 |
| `clear_position` | **一條測試都沒有**——整個函式改成 no-op，406 條全綠 |
| M003／M999 | 兩者被欄位數檢查先擋掉，前綴判斷是死碼 |
| 成交查詢的市場別 | 委託查詢那側有測，成交查詢這側漏了——而真正加總口數的是這一半 |

全部補上，並用突變測試確認每一條都真的會紅。

## 實作備註

**`GetFulfillReport` 的已知限制**（官方文件）：

| 限制 | 影響 |
|---|---|
| 「查詢為阻塞式，請以執行緒方式進行查詢」 | 會卡住程式幾秒。08:50 可以接受，但要設上限 |
| 「限制每次查詢間需間隔五秒」 | 所以只查一次，不做重試迴圈 |
| 回傳以 `,` 分隔、`\r\n` 換行 | 又一組沒實機驗過的欄位位置——同一類風險 |
| `M003: 查無資料` / `M999: 查詢錯誤` | 這兩個要分開處理：查無資料≠查詢失敗 |

**⚠️ 不要用 `GetOpenInterest`（未平倉查詢）代替。** 它回的是**淨額**：
台指期同帳戶同商品同月份採淨額計算，使用者自己的固定持有部位會混在裡面，
分不出哪幾口是 OS 開的（見 CONTEXT 的「固定持有部位」）。
`GetFulfillReport` 查的是我們自己送出的委託，沒有這個問題。

**這張是強化，不是修 bug。** 沒有它系統也是正確的，只是遇到回報延遲時
會要求人工介入。所以優先順序低於 06、07。
