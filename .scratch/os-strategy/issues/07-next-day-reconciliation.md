# 07 — 隔日對帳

**What to build:** 隔天早上，在當日的訊號、通知、下單全部完成**之後**，
程式比對前一交易日記錄的三個開盤價與期交所官方資料。不一致就發 Discord。

這是唯一能抓到「開盤價取到錯誤盤別」這類系統性錯誤的機制——那種錯誤會讓每天的訊號都錯，
但從數字本身完全看不出來。它是純加分功能，偶爾失敗只是少檢查一天。

**Blocked by:** 04

**Status:** 程式完成（326 tests passed）。**對帳邏輯已用真實期交所資料驗過**；
累積幾週樣本後要回來決定那 2 點差異要不要容差

- [x] 對帳在訊號發報與下單全部完成之後才執行，時序上不可能耽誤當日策略
      —— 包在 `run_entry` **外面一層**而不是塞進流程裡：策略流程有 6 個提前返回的
      出口，逐一補會漏；包在外面只有一個地方要顧。
- [x] 對帳的任何失敗（網路、格式、例外）都不影響當日策略，也不改變程式的結束狀態
      —— `run_reconciliation` **保證不拋例外**，`test_reconcile.py` 有一整組
      「餵它壞東西」的測試（壞掉的觀測檔、斷線、缺商品、值不是數字、webhook 500）。
      ⚠️ 預設取數函式刻意**延後 import**：在 `run_entry` 裡 import `taifex` 的話，
      import 失敗會冒出保護傘之外——而那時候單已經送出去了。
- [x] 官方資料的日期與狀態檔記錄的日期不符時**靜默跳過**，不視為失敗
      —— 實作成「取 `today` **之前**最近的一筆觀測」。今天的觀測 08:50 才寫進去，
      期交所還沒公布當日資料，拿它去對會每天都查無資料而等於從來沒跑過。
- [x] 三個開盤價與官方資料一致 → 只寫 log
- [x] 任一不一致 → 發 Discord，指明哪個商品、兩邊各是多少
      —— 三個同時不一致時訊息會多一句「這比較像取到錯誤的盤別」，
      因為那正是本張要抓的那個錯誤的樣子。
- [x] 比對在數值域進行，不比對字串

## ⛔ 開工前必須先解決：對帳的資料來源不存在

**2026-08-17 盤點時發現：本張的前提「前一交易日記錄的三個開盤價」根本沒有被寫下來。**

| 需要 | 現況 |
|------|------|
| 三個開盤價要能隔天讀到 | `PositionRecord` **沒有這些欄位**。`opens` 只活在記憶體與 Discord 訊息文字裡 |
| 每個交易日都要有紀錄 | 訊號為**不動作**時完全不寫狀態檔（佔 23.2% 的交易日） |
| 開關關閉時也要有紀錄 | **完全不寫**——而那是現在每一天的狀態 |

最後一條與 SPEC 的上線計畫直接矛盾：

> 自動下單預設關閉。**第一階段可只跑訊號，用零金錢風險驗證資料正確性**，
> 確認無誤後再開啟下單。

**「驗證資料正確性」的機制就是本張，而它依賴只有下單才會產生的資料。**
第一階段跑訊號的那段期間，對帳無事可做——那卻正是最需要它的時候
（開盤價取到錯誤盤別會讓每天的訊號都錯，而從數字看不出來）。

### 因此本張要先做的事 —— ✅ 2026-08-18 完成

- [x] **每個交易日都寫一筆「當日觀測」**，內容至少含三個開盤價與訊號方向，
      且**與部位記錄分開** —— `observations.py` / `state/observations.jsonl`
- [x] 不動作的日子照寫
- [x] 自動下單關閉時照寫
- [x] 決定保留多久／要不要輪替 —— **不輪替**。一天一行、一年約 250 行、
      幾十 KB。加輪替的複雜度比省下的空間貴。

額外做的兩件事（原本沒寫進驗收條件，但做下去才發現該有）：

- [x] **同一個交易日不重複寫。** `run_entry` 的重複執行保護看的是部位記錄，
      而開關關著時根本不寫部位記錄——那條防線在觀測這一側完全攔不住。
- [x] **同一天第二次跑而數字不同 → 拋 `ObservationConflict`，檔案不動。**
      同一天出現兩組不同的開盤價本身就是要看的東西，靜靜丟掉一組等於銷毀證據。

- [x] 用 JSONL 而不是單一 JSON 陣列：append 是一次寫入，不必先讀進整份再寫回去。
      後者中途失敗會毀掉**歷史**，而這份檔案的價值正是歷史。

⚠️ 這不是把欄位塞進 `PositionRecord` 就好。那個型別的不變量是繞著
「OS 開了什麼部位」建立的（`lots` 與 `status` 綁死、`CONFIRMED` 必須有口數），
把「今天沒有部位但有觀測」硬塞進去會破壞那些不變量。

## 已觀察到的實際差異（供實作時參考）

2026-08-10 實測，群益與期交所在**大台**上對不起來，小台微台卻一致：

| | 群益 | 期交所 一般 |
|---|---|---|
| 大台 開盤 | 44987 | **44985** |
| 大台 高／低 | 45219 / 44668 | **45148 / 44832** |
| 小台 開盤 | 45000 | 45000 ✅ |
| 微台 開盤 | 45007 | 45007 ✅ |

而 2026-08-07 三個是完全一致的。已排除「讀太早」（等 39 秒不變）與
「連續合約」（指定月份的 `TX08AM` 給同樣的值）。

**📌 2026-08-14 與 08-17 的樣本：`nOpen` 與第一筆真實成交（時間戳 084500）
三商品完全一致**（08-17：45850／45812／45863）。加上 08-07，
目前 4 個樣本中只有 08-10 那次不一致——**那個 2 點的差異是間歇性的，不是常態**。
樣本自 2026-08-16 起由 `tools/compare_open.py` 累積在
`captured/open-price-samples.jsonl`。

原因未明——可能是期交所當日公布的暫定值，也可能是群益大台開盤欄位的偏差。
**手上的資料不足以判定**：群益的報價只有當天，拿不到歷史來統計。

→ 這正是本 ticket 存在的理由。先照原樣做（不一致就報），累積幾週再決定
　 要不要容差。**不要**因為這個觀察就預先加上容忍值——那會把真正的錯誤一起放過。

**實作已照此辦理**：`reconcile._EPSILON = 1e-6`，那是浮點數表示誤差的容許量，
**不是容差**——2026-08-10 那 2 點照樣會被報出來，有測試釘著
（`test_a_two_point_difference_is_still_reported`）。

## code-review 抓到的東西（2026-08-18）

初版是**兩支平行子代理**跑出來的：一支比對本專案的文件標準，一支比對本張的驗收條件。

| # | 問題 | 後果 |
|---|------|------|
| 1 | **一行壞掉 → 整個稽核能力永久消失** | append 讀不到既有記錄 → 再也寫不進觀測；對帳每天在「讀不懂」返回 → 永遠不再對帳。**而且全程只進 log，一則 Discord 都不發** |
| 2 | 組 Discord 訊息的 `import` 放在 try **外面** | import 失敗會冒出 `run_reconciliation` → 而那時候單已經送出去了，整班以 traceback 結束 |
| 3 | 告警用 `{:.0f}` 把數字四捨五入 | 比對門檻是 1e-6，小數差異**會**觸發告警，卻印出兩個一模一樣的數字 |
| 4 | `fetch_ohlc` 從不驗回傳列的交易日期 | 期交所若改行為（回最近一天而非指定日），會拿別天的資料去比對，報一個看起來很真實的不一致 |
| 5 | `ObservationConflict` 被唯一的呼叫端吞成 log | 這個例外形同虛設——同一天兩組開盤價沒有人會知道 |
| 6 | `tools/compare_open.py` 的 `taifex_open` 只剩 `return fetch_ohlc(...)` | Middle Man，已刪 |
| 7 | yyyymmdd 轉字串那串運算式逐字重複在兩個檔 | 已抽成 `broker.format_yyyymmdd` |
| 8 | `run_entry` / `_run_entry` 只差一條底線 | 已改名為 `_run_strategy`，並把三層巢狀三元式拆開 |

**第 1 項最嚴重，而且諷刺**：那正是本張票要防的那種錯誤——安靜地、
永久地失效而看起來完全正常——發生在它自己身上。

初版的設計是「讀到壞行就拋例外」，理由寫得很好聽：「讀不懂當成沒有的話，
對帳會靜默跳過而沒有人知道它壞了」。那個顧慮是對的，但那個解法更糟。
**現在改成：壞行跳過（其餘照常運作）＋ 發 Discord 告警。**
原本的顧慮由「回報」滿足，不必靠「停擺」。

兩項**確認沒問題**：`_EPSILON = 1e-6` 沒有偷渡容忍值（2026-08-10 那 2 點照樣會報，
有測試釘著）；`run_exit` 不需要改（觀測是 08:50 的開盤價，對帳必須在進場那班之後）。

兩項**確認為超出範圍、記下不做**：`trading_day: int` 的 Primitive Obsession
（整個專案都用裸 int，引入型別是跨模組重構）、三商品的知識散在三張表
（`taifex.COMMODITIES` / `reconcile._PRODUCTS` / `broker.TX_CODE`，收攏要動 `broker/`）。
