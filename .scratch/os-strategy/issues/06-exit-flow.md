# 06 — 出場流程

**What to build:** 到了出場時間，程式讀取當日進場記錄，送出**等量反向**委託平倉。
失敗會自動重試；三次都失敗時發出 Discord 告警，讓使用者能立刻手動處理，
不會在不知情的狀況下讓部位進入夜盤。

**Blocked by:** 05

**Status:** ready-for-agent

- [ ] 出場委託的口數等於狀態檔記錄的**實際成交口數**，方向與進場相反
- [ ] 出場委託為市價 IOC
- [ ] 狀態檔無當日記錄，或當日訊號為不動作 → 什麼都不做
- [ ] 出場失敗時每隔一分鐘重試，最多三次
- [ ] 三次都失敗 → 發 Discord 告警，訊息內容足以讓使用者判斷該手動平掉什麼（商品、方向、口數）
- [ ] 結算日的出場時間為 13:30，**且不重試**（合約已停止交易，未平倉部位由交易所現金結算）
- [ ] 出場成功後更新狀態檔
- [ ] 例行出場**不發** Discord，只有失敗才發
- [ ] 時間由參數傳入而非讀系統時鐘，測試可直接指定結算日與一般交易日
- [ ] **前兩次出場失敗、第三次成功 → 正常完成，不發告警**
      （證明重試真的會再試；不斷言間隔或呼叫次數，那是實作細節）

## 從 ticket 05 接手的部分

05 建好了「不確定」這個狀態與它的契約（`PositionRecord.is_uncertain`、
`lots` 在不確定時為 `None`），但**執行端在出場流程，而出場流程是這張**。
所以下面這幾條由 06 負責，05 那邊已標為待本張完成：

- [ ] 狀態為「不確定」時（`record.is_uncertain`）→ **不送出任何委託**，
      改發 Discord 要求人工處理
      —— 不知道持有幾口就下單，可能開出反向新倉，比什麼都不做更糟
- [ ] 出場後比對「應平口數」與「實際成交口數」，有殘留 → 發 Discord 告警，
      訊息含商品、方向、**殘留幾口**，足以讓使用者直接手動處理
- [ ] **部分成交不視為出場成功**，狀態檔不可標記為已出場

⚠️ **`record.lots` 的型別是 `int | None`。** 上面第一條驗收條件就是 `None` 的處理；
先檢查 `is_uncertain` 再用 `lots`，直接拿去當口數會把 `None` 送進委託。
