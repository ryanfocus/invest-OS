# 05 — 部位一致性防護

**What to build:** 系統**絕不在「不確定自己持有什麼」的狀態下靜默結束**。
送單後收不到成交回報、或平倉後還有殘留口數，都要留下明確記錄並發 Discord 要求人工介入。

這是本系統唯一會直接虧錢的失效模式：帳上有部位、程式卻不知道，於是 13:40 不會去平它，
部位就這樣進了夜盤（15:00–05:00），而使用者完全不知情。

**Blocked by:** 04

**Status:** done（2026-08-18）—— 進場側自己做，出場側三條由 [ticket 06](06-exit-flow.md) 落地並驗過

## 送單後收不到成交回報

- [x] 送出進場委託後，在設定的時限內未收到成交回報 → 狀態檔記為**「不確定」**
      （已送單、成交口數未知），並發 Discord 要求人工確認帳戶
- [x] 逾時秒數由設定檔決定，且該設定確實被程式讀取（沿用既有的設定漂移檢查）
- [x] 「不確定」與「確定沒有部位」在型別上不可能混淆
- [x] 重跑時看到不確定的記錄**不會再送一次單**（那有一半機率變成兩倍部位）
- [x] 狀態為「不確定」時，出場那班**不自動送出任何委託**，改發 Discord 要求人工處理
      —— 不知道持有幾口就下單，可能開出反向新倉，比什麼都不做更糟
      ✅ **ticket 06 已落地**（`build_exit_blocked_payload`）。
      💡 結算日遇到不確定的記錄走的是另一條：部位會被交易所結算，
      所以改成「告知＋請自行對帳」，不是「請手動平倉」——後者做不到。

      訊息含商品、方向、**殘留幾口**，足以讓使用者直接手動處理
- [x] **部分成交不視為出場成功**，狀態檔不可標記為已出場

## 為什麼出場側留給 06

這張 ticket 的驗收條件橫跨進場與出場，而出場流程要到 06 才存在。
硬要在這裡做完，等於先寫一個沒有人呼叫的出場函式，再回頭改它——
測試會變成在驗「我想像中的出場長什麼樣」，那正是 `/tdd` 說的 horizontal slicing。

所以這裡做的是**機制與契約**：

- 「不確定」這個狀態本身（`state.UNCERTAIN`）
- 它與「0 口」在型別上的隔離（`PositionRecord.__post_init__`）
- 出場那班要問的那一個問題（`PositionRecord.is_uncertain`）
- 進場側的完整行為（記錄、告警、重跑不重送）

06 建出場流程時直接用這套，順手把上面兩個 ⏳ 補完。

## code-review 抓到的東西（2026-08-15）

初版 commit `af935b4` 之後跑了雙軸 review。**最嚴重的一個是這張 ticket
自己那句話被我自己違反了**——「系統絕不在不確定自己持有什麼的狀態下靜默結束」。

| # | 問題 | 後果 |
|---|------|------|
| 1 | 委託回報（N）在成交回報之前先到，而等待條件是「認出至少一列」 | **單還在市場上就收工**，回報 0 口、不寫檔、不發通知 |
| 2 | 送單成功後的例外（COM 壞掉、幫浦拋錯）走到 `OrderFailed` | 同上，說成「確定沒有部位」 |
| 3 | `%d` 遇到 `lots=None` 會讓整行 log 消失 | 13:40 排查時要找的正是那一行 |
| 4 | 不確定記錄沒存委託序號與委託口數 | 使用者得從幾百筆委託裡自己找，也不知道曝險上界 |
| 5 | 不確定之後重跑會靜默結束 | 看起來像「已經沒事了」，但帳上可能還有部位 |
| 6 | `read_position` 寫在 `except` 區段裡 | 那次讀若拋 `StateCorrupted`，例外逃出而一則通知都不發 |

第 1 項的正解是問「**這筆委託結束了沒**」而不是「有沒有收到回報」。IOC 的結局
只有三種：被拒、剩餘量取消（`C`）、全部成交。見 `FillSummary.is_settled()`。

第 2 項的界線是 `SendFutureOrderCLR` 回 0 那一行：**過了它，單就在市場上**，
之後任何失敗都是 `FillUnknown`。這條保證只活在那段 try 裡，而那段要有 COM 才跑得到，
所以破例寫了一個塞假協作物件的測試（`tests/test_post_send_failures.py`）——
突變證實沒有它的話，拿掉 `except Exception` 那條，211 個測試依然全綠。

**順帶修掉一個 SPEC 與實作的衝突**（兩個 review 都沒看到，它們只看 05 的 diff）：
SPEC 寫「**不可**使用商品代號 + 月份兩碼」，而 ticket 04 實作的正是那個。
偏離的理由是微台的 CID 官方全文沒有記載。補償措施是 `ContractInfo.has_expired()`——
最後交易日已過就拒絕送單，直接消滅「自動改送隔年同月」那個風險。
SPEC 已記錄偏離與補償。

## 實作備註

**`FillUnknown` 與 `OrderFailed` 是這個系統最貴的一條分界線。**

```
OrderFailed  → 確定沒有部位 → 下午什麼都不用做
FillUnknown  → 可能已經成交 → 下午絕不可以自動送單，要人去看帳戶
```

ticket 04 的時候只有 `OrderFailed`，逾時被迫用它表達，而 `capital.py` 的註解
標明了那樣並不精確。現在分開了。

**寫檔在拋例外之前。** `_place_entry_order` 收到 `FillUnknown` 時先寫「不確定」記錄
再 `raise`。順序反過來的話，中途出任何事就什麼記錄都沒有，
下午那班會以為今天沒進場——而那正是這張 ticket 要擋的事。

**`lots=None` 不是 `lots=0`。** 0 的意思是「確定沒成交」。用 0 表示不確定的話，
任何 `lots > 0 才處理` 的判斷都會靜靜跳過這筆記錄，而它正是最需要有人來看的一筆。
`PositionRecord.__post_init__` 把口數與狀態的關係綁死，兩者在型別上不可能混淆。

**Discord 訊息刻意與「下單失敗」不同。** 下單失敗的正確反應是「不用管」，
成交未確認的正確反應是「馬上去看帳戶」。長得一樣的話，最需要行動的那一則
會被當成又一個雜訊。
